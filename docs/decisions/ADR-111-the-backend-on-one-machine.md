# ADR-111: The backend on one Compute Engine machine, the budget shape

- Status: Accepted
- Date: 2026-11-12
- Deciders: the owner (chose this shape over the managed one when the costs were laid out),
  Claude Code (implementer)
- Amends: ADR-110 (a third shape beside `live/` and `backend/`), ADR-059 (the topology),
  ADR-060 (how a release reaches the environment), ADR-038 (plaintext between containers on
  one host)

## Context

ADR-110 put the backend on Cloud Run, Cloud SQL and Memorystore. When the deployment was about
to start, two facts about the owner's account changed the plan:

- **Money.** The managed shape costs roughly 130 to 230 US dollars a month from the day it is
  created: a managed database, a managed cache and a worker that never sleeps. The owner had
  just been unable to fund a 50 dollar deposit on a new billing account.
- **Billing.** The owner's one open billing account was at Google's limit of five projects. The
  owner chose which finished project to unlink, and the backend's own project,
  `suskii-travels-staging`, took its place. The owner's two existing `suskii-staging` and
  `suskii-prod` projects belong to another Suskii app with its own Terraform and were left
  alone: both apps name an Artifact Registry repository `suskii`, so they would collide.

Asked to choose between the managed shape, one small machine, or waiting, the owner chose the
machine.

The owner's standing requirement is unchanged: the assistant's backend is deployed with the
platform's, and nothing about the assistant may make the platform misbehave.

## Decision

### One machine, the same containers

`infra/terraform/vm/` creates one Compute Engine VM (`e2-medium`, Debian 12, London) with a
fixed public address, and `infra/gcp/vm/compose.yml` runs on it:

| Container  | What                                                        | Reachable from      |
| ---------- | ----------------------------------------------------------- | ------------------- |
| `caddy`    | HTTPS, a certificate from Let's Encrypt, the only open port | the internet        |
| `api`      | the API's release image                                     | Caddy, the others   |
| `worker`   | the worker's release image                                  | nobody              |
| `agent`    | Ask Suskii's own service                                    | the API only        |
| `postgres` | PostgreSQL 16, data on the data disk                        | the three above     |
| `redis`    | Redis 7 with a password, writes logged to the data disk     | the API, the worker |

The compose file is `docker-compose.release.yml` with real keys: the same images, settings,
read-only file systems, dropped capabilities and "no new privileges" that CI rehearses on
every change. No application code changed for this shape.

- **Keys** are in Secret Manager, as in the managed shape, generated by
  `scripts/gcp/seed-secrets.mjs` and never printed. The machine reads them as its own identity
  at each release and hands each container only its own: the worker gets one token, the agent
  service its two tokens, its model key and its own database address, and nothing of the API's.
- **Data** lives on a disk of its own, which outlives the machine. A dump of the database goes
  to a private bucket every night; the bucket deletes it after 30 days, and the machine may
  add a dump but cannot read, replace or delete one. Fields the API encrypts stay encrypted in
  a dump, and their key is not in the bucket.
- **The name.** Until the owner has a domain the API answers on Google's free name for the
  project, `api.endpoints.<project>.cloud.goog`, which Terraform points at the machine's
  address. With a domain, `api_host` names it and its DNS record points at the same address.
- **The internal routes** (`/v1/internal/*`, for the worker and the agent service) answer 404
  at Caddy. The two reach the API on the private network, never through the front door.
- **No login.** A release is named in the machine's metadata (`suskii-release`); a watcher on
  the machine deploys it and writes the outcome to the serial console and to a guest attribute
  the operator reads. SSH is open only through Identity-Aware Proxy, for people the project
  lets in, and nothing in a release uses it.

### The assistant cannot take the platform down

On one machine the separation of ADR-101 is kept by other means than separate services:

- The agent service is its own container with its own tokens, its own model key and its own
  database role, which sees only the `agent` schema (ADR-103). It reaches the platform only
  through the tool gateway.
- It has a ceiling of 512 MB of memory and three quarters of a processor. A runaway assistant
  is stopped by the kernel at that ceiling; the API, the worker and the database keep theirs.
- A release brings the platform up first and the assistant last. If the assistant does not
  come up the release still stands, and says so.
- The API never waits on it. With the container stopped, every platform route answers as
  before (checked on the stack before the first deployment). A chat then ends with the
  "unavailable" notice; `GET /v1/agent/status` reports the switch, not the container, so the
  button stays until the assistant is switched off (`ASSISTANT_ENABLED=false`) or paused.
- The spend caps and the pause switch are unchanged.

### One command

`scripts/gcp/deploy-vm.sh <project> [region] [zone]` applies the Terraform, gives the secrets
their values, builds the four images with Cloud Build, names the release, waits for the
machine's own report and checks the public address. It can be stopped and run again.

## What this shape gives up

Said plainly, because the owner chose it for its price:

- **One machine.** A restart, a kernel update or a zone outage takes the backend down until it
  is back. The managed shape has no such single point.
- **The database is ours to look after.** Backups are a nightly dump (up to a day of loss) and
  whatever is on the data disk. There is no point-in-time recovery and no failover.
- **No WAF and no load balancer.** Rate limits and bot checks are the API's own. The managed
  shape behind Cloudflare has both. The machine has a public address, which the configuration
  scan reports (Trivy GCP-0031): it is accepted here with an expiry of 2027-04-30, when the
  scan fails again and the choice is looked at.
- **Plain connections between containers.** They share one private bridge network on one
  host, so nothing between them leaves the machine; the `*_ALLOW_PLAINTEXT` settings say so
  (ADR-038). It is not encryption.
- **Keys reach the machine's disk.** Docker keeps a container's settings in its own files,
  readable by root only, on a disk Google encrypts at rest.
- **The stand-ins.** Suppliers, payments, email, texts and push are the built-in mocks until
  the owner connects real accounts, as in ADR-110. No real money moves.

It is a staging backend and a way to put the app in people's hands. It is not where paying
customers' bookings should live once there is revenue.

## Moving up later

Nothing in the application changes. The managed shape (`backend/`, then `live/` with the
domain) takes the same images and the same secrets: restore the last dump into Cloud SQL, give
the API the new addresses, point the name at the new front door, and stop the machine.

## Alternatives considered

- **The managed shape now.** Ready and planned against the project, at four to six times the
  monthly cost.
- **Cloud Run for the API and the agent service, the machine for the data and the worker.**
  Cheaper still at rest and with Google's own HTTPS, but it needs the platform module taught
  to use a database it does not create. Worth doing when traffic makes one machine tight.
- **A free tier machine.** Google's free `e2-micro` has 1 GB of memory and is offered in three
  United States regions only. The five containers do not fit.
- **Deploying into the owner's existing `suskii-staging` project.** Refused: another app's
  Terraform owns it.
- **Waiting.** Offered; the owner preferred to go live.
