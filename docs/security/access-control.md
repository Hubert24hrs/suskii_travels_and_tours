# Access control

The rules that decide who may call what, see which records, and read or write which fields
(ASVS V8.1). The API enforces all of them. The web, app and console only hide what a person
cannot use. Designs: ADR-007 (authorisation), ADR-015 (guest access), ADR-033 and ADR-034 (admin).

## Function level

- **Authenticated by default.** Every route needs a session unless it is marked `@Public()`.
  Public routes are search, catalog and content reads, sign-up and sign-in, guest checkout,
  webhooks, health probes, web-vitals beacons, AI trip search (`/v1/flights/natural-search`,
  which fills a form and reads nothing private; ADR-061), partner offers for a place, the
  sealed partner redirect (`/v1/go/{token}`) and network postbacks, which need the network's
  secret (ADR-070), published reviews (`/v1/reviews`, ADR-077), route facts, city hubs and
  airline pages (`/v1/deals/...`, priced fares only, ADR-080), the metasearch price API, which
  needs a partner key instead of a session, metasearch landings, which need a sealed deep
  link (`/v1/metasearch/...`, ADR-081), and starting a support conversation, which needs
  Turnstile or a device attestation without a session (`/v1/support/conversations`, ADR-083).
- **Permissions, not roles, in code.** Routes declare `@RequirePermissions(...)`. Admin routes
  declare `@AdminRoute(permission)`, which also requires a staff role, an MFA session, an
  allowlisted IP and, for cookies, an allowlisted origin. The riskiest admin mutations add
  `@StepUp()`.
- **One catalog.** `ROLE_PERMISSIONS` (`packages/shared/src/rbac.ts`) maps the ten roles
  (`customer`, `super_admin`, `operations`, `finance`, `support`, `content_manager`,
  `visa_officer`, `privacy_officer`, and the Cars roles `driver` and `operator_agent`) to 32
  permissions. The seed syncs it to the database for the console. Drivers and operator agents
  are not staff (`NON_STAFF_ROLES`): no console, no MFA requirement, and their routes also check
  the record (the driver assigned to a ride, the agent's operator) (ADR-049, ADR-050).
- **Switched-off products.** A disabled Cars product (`CARS_*_ENABLED`) answers 404 on all its
  routes, before authentication (`CarsFeatureGuard`).
  AI trip search with `AI_SEARCH_ENABLED` off answers 404 on its parse route; its status route
  says it is off. Partner offers with `PARTNER_OFFERS_ENABLED` off answer 404, and postbacks
  answer 404 while the network has no postback secret.
- **Checked automatically.** The OpenAPI build fails for an admin route without a permission or
  audit list. `admin-matrix.e2e-spec.ts` calls every admin route as every role and expects 403
  unless the role holds the permission. Denials are audited (`rbac.access_denied`) or logged
  (`authorization denied`).
- **The assistant's tools** (`/v1/internal/agent-tools`, ADR-101, ADR-107) accept only the agent
  service's own token (`AGENT_TOOLS_TOKEN`; the worker's token opens nothing there, and the
  agent's opens none of the worker's routes) and answer 404 while `AGENT_ENABLED` is off. A
  call then runs only for a grant the API sealed for a running run (the caller, roles, channel
  and scopes are inside it and are never taken from the model), for a tool that is the calling
  agent's, inside the grant's scopes, at an autonomy level that lets its tier run, and within
  the run's call limit. A `commit` tool never runs from the gateway. Approving a refund,
  capturing a payment, paying out, posting to the ledger, changing a price rule and confirming a
  booking cannot be registered as tools at all (`isForbiddenAgentTool`; the API refuses to
  start). `test/agent-gateway.e2e-spec.ts` covers each refusal.
- **The tools themselves** (ADR-107): 45. Thirty-two are the customer agents', each calling
  the ordinary service as the grant's caller (`BookingsService.load()`, `TripsService.get()`,
  `SupportService.start()`), so another person's booking, trip, quote or conversation is
  `not_found`, as the API answers 404. Twenty-three of them only read. Three prepare something:
  `trips.plan` starts a combined trip for the signed-in traveller (it books and holds nothing),
  `support.handover` opens one support conversation with the traveller's own last messages,
  and `quotes.request` asks staff to confirm a price (ADR-104). Six commit and never run from
  the gateway (`bookings.cancel`, `changes.accept`, `changes.take_refund_offer`,
  `alerts.watch`, `alerts.stop`, `memory.remember`): each becomes a confirmation. A guest's
  grant carries no `account` scope, so the bookings, payments and trips tools are refused
  before they run. Ten are the staff agents', in the console only: seven read counts, amounts,
  ids and codes and three prepare a proposal for the approvals queue (a refund request, a
  promo code, a recipe for a site). Three (`catalog.places`, `knowledge.search`,
  `platform.status`) are for every agent; what `knowledge.search` reads is decided by the
  grant's audience, never by an argument. The snapshot `apps/agent/evals/tools.json` is the
  registry as the API serves it. `test/agent-tools.e2e-spec.ts` covers the customer tools,
  `test/agent-staff.e2e-spec.ts` the staff tools, and `test/agent-service.e2e-spec.ts` the
  chain with the agent service as its own process.
- **Confirmations** (`/v1/agent/confirmations/{id}`, ADR-107): the card and the tap belong to
  the signed-in owner of the conversation (404 for anyone else, 401 without a session). The
  tap carries the traveller's session and an `Idempotency-Key`, claims the row with a
  conditional update and runs the tool with a grant built from that session; the agent service
  holds no route to it. A new message, 15 minutes or a changed fact ends a card without doing
  anything; a tap is refused while the assistant is paused.
- **Assisted quotes** (ADR-104): a request, its offer and its booking belong to the account
  that asked (404 for anyone else, also on the offer's quote and at booking). Staff with
  `ai:read` see the queue; `ai:approve` records the verified price or closes a request;
  `bookings:manage` records the supplier's confirmation or marks a paid booking unbookable
  (which refunds it). Every change is audited. While `ASSISTED_QUOTES_ENABLED` is off a
  traveller's routes answer 404, no offer is made and none can be paid for; staff can still
  finish or close what is open.
- **Staff agents and approvals** (`/v1/admin/ai`, ADR-107): staff with `ai:read` talk to the
  agents whose scope their own permissions open (`STAFF_AGENT_SCOPES`), and every tool is
  checked against the grant's scopes again; a conversation and its runs are their owner's
  alone (404 for other staff, and for the travellers' routes). What an agent prepares is a row
  in `agent_approvals`. Deciding it needs `ai:approve`, the kind's own permission
  (`refunds:request` for a refund request, `deals:manage` for a promo code,
  `datasources:manage` for a site's recipe) and to be someone other than the person who asked
  (403 `own-approval`); approving runs the ordinary service as the approver, so a refund
  request still meets its own second approver, and a recipe is saved through the ordinary site
  update only while the site still has the recipe the proposal replaces (409 `recipe-changed`
  otherwise). No tool decides an approval (`isForbiddenAgentTool`).
- **The assistant's chat routes** (`/v1/agent/*`): a conversation opens to its owner's session,
  or to a guest's token shown once after a human check and stored as an HMAC (`agent-access`);
  a run, its events and a thumb on an answer belong to the conversation they are part of.
  Anyone else gets 404. The routes answer 404 while `AGENT_ENABLED` is off.
- **Price intelligence** (`/v1/admin/data-sources`, ADR-102): seeing sites, reads, observations
  and the register needs `ai:read`; listing, changing, deciding and reading a site, the
  switches and the budgets need `datasources:manage`. Approving a site, switching reading back
  on and changing a budget also need step-up; switching off does not. An approval is refused
  until someone recorded what the site's robots file and terms say, and takes only a licence
  or a permission when either disallows automated access. Changing what an approver agreed to
  (vendors, proxy class, findings, page addresses, rate) sends the site back to review. A
  blocked site cannot be approved directly (409 `price-source-blocked`): it goes back to
  review first. The
  sweep (`/v1/internal/price-intel/sweep`) takes only the worker's token. The agent service has
  no route here and holds no vendor key: it reaches prices only through tools. A recipe for a
  site in drift is worked out by a rule from the page that was kept (`sources.propose_recipe`,
  scope `datasources`); it names only schema.org types from our own list, changes nothing, and
  waits in the approvals queue. A recipe is how a page is read, not what the approver of the
  site agreed to, so saving one does not send the site back to review.
  `test/price-intel.e2e-spec.ts` covers each rule.
- **Internal routes** (`/v1/internal`) accept only the worker's service token. Behind
  Cloudflare the edge also blocks them, and blocks the console and `/v1/admin` from addresses
  outside `admin_allowed_ips` (ADR-059).
- **Database roles.** The API connects as `suskii_app`, which may only read and write rows;
  migrations run as the schema owner from the migrate job only (`apps/api/src/infra/app-role.ts`,
  ADR-059). A SQL injection could not change the schema, truncate tables or create roles.
- **The first super admin.** Roles change only in the console (step-up, audited), which needs a
  super admin. A new environment gets its first one from `staff:bootstrap` (the `ops` job in a
  deployed environment): it grants `super_admin` to an existing account with a verified email,
  records `rbac.roles.changed` as a system action, signs the account out, and refuses once any
  super admin exists (`test/staff-bootstrap.e2e-spec.ts`). `SEED_ADMIN_*` stays local only.

## Field level

**Read.** Each response is filtered through the route's response schema. Fields not in the
schema never leave the API.

| Field                                   | Rule                                                                                    |
| --------------------------------------- | --------------------------------------------------------------------------------------- |
| Markup, supplier cost, pricing rule ids | Never in any response, for any role                                                     |
| Booking contact (email, phone)          | Masked for everyone. Staff with `bookings:read` can reveal it with a reason, audited    |
| Passport numbers                        | Last three characters only, for everyone, staff included                                |
| Voucher codes                           | The owner sees their own; staff redeem by code and see the redemption state             |
| Payment details                         | Provider, status, amounts and references; never card data (the platform has none)       |
| Account details in the console          | Profile, roles, status, MFA state and sessions; never password hashes, secrets or codes |

**Write.** Each request body is parsed by a schema listing the fields that action may set. Zod
drops unknown fields before the handler runs, which prevents mass assignment.

| Field or change                       | Rule                                                                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Booking status                        | Only through `BookingTransitions.apply()` under the state machine; never set from a request               |
| Prices and totals                     | Only computed by the API from the offer, pricing rules and the ledger                                     |
| Roles                                 | Only `roles:manage` with step-up, never on one's own account                                              |
| Trust signal `verified`               | Only `trust-signals:verify` with an https evidence URL; any edit clears it                                |
| Markups, fees, tax rules, Prime plans | Only `pricing:manage` with step-up; a `full` tax rule on Cars is refused while `CARS_VAT_BPS` is set      |
| Refund approval                       | Only `refunds:approve` with step-up, and never by the staff member who requested the refund               |
| Catalog and content records           | The merged record is re-validated with the public schema (`checkMerged`); changed field names are audited |

**State.** Some rights depend on the record's state:

- Self-cancellation follows the product's tiers. Visa assistance and memberships cannot be
  self-cancelled.
- Payment plans take no paid extras.
- Refunds never exceed what the source still holds.
- A booking held for a risk review is not fulfilled until finance approves it.
- The full refund for an airline change (ADR-073) is open only on a confirmed flight with an
  open, significant change, before departure. The airline cancels first, and the refund is
  taken online only when the airline's refund covers what we paid it; otherwise support takes it.

## Changing the rules

1. Add the permission to `PERMISSIONS` and the roles that hold it to `ROLE_PERMISSIONS`.
2. Declare it on the route. Admin routes also list their audit actions.
3. Add an admin console navigation entry whose permissions match the route.
4. Run the admin e2e matrix and audit suites; a new admin mutation needs a case in
   `admin-audit.e2e-spec.ts`.
5. Update this page if a data or field rule changed.
