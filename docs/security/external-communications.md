# External communications

Every connection the platform makes or accepts beyond its own components, and the rules for
each (ASVS V13.1.1, V12.3). Keep it current: a new provider or host needs an entry here, a
setting in `.env.example`, and a production check in the API's environment schema.

## Rules for every outbound call

- **TLS.** HTTPS with certificate verification on every call. No call sets
  `rejectUnauthorized: false`.
  - Production refuses plain http for providers, the worker-to-API hop, Postgres, Redis and the
    OTLP collector. The only exceptions are the declared `*_ALLOW_PLAINTEXT` private paths
    (ADR-038) and a collector on localhost.
  - SMTP requires TLS in production (implicit TLS, or STARTTLS made mandatory).
- **Fixed destinations.** Hosts come from configuration or constants, never from a request. The
  one user-influenced fetch is `next/image`, which only loads `https` images from the hosts in
  `IMAGE_REMOTE_HOSTS`. Trust-signal evidence URLs are stored and shown to staff, never fetched.
  Price intelligence reads sites staff listed and approved: its hosts come from that registry,
  under the rules in "Reading other sites" below.
- **No redirects.** HTTP calls use `redirect: 'error'`, so a compromised or misconfigured
  endpoint cannot bounce a credential to another host.
- **Redirects we send.** `/v1/go/{token}` sends browsers only to a destination the API sealed
  into the token, on that partner programme's own hosts, or to a tracked link on Travelpayouts'
  hosts (no open redirect, ADR-070).
- **Timeouts.** Every call has a deadline.
- **Vendor isolation.** Payloads are parsed and mapped inside the adapter. Vendor types never
  leave it (supplier and payment adapter conventions).
- **Least data.** Each provider receives only what its job needs (below).

## Reading other sites (price intelligence, ADR-102)

This is the one place where the host of a server-side request is not a constant or a setting.
The rules that make that safe:

- **The host comes from the registry.** A site is a row staff created (`datasources:manage`),
  and it is read for real only once approved, which takes a second authenticator check and a
  recorded basis. A site in `review` is answered by the mock vendor only, which fetches
  nothing; production has no mock. A `blocked` site is never read.
- **The address is built by the API.** A page address is a template stored with the site,
  filled with checked values (airport codes, a place name, dates, head counts), each
  URL-encoded. No model, tool argument or traveller supplies an address or a host.
- **Checked before any fetch** (`assertFetchable`): https only, no credentials, the default
  port, a host name and never an IP literal, on the site's own domain or a subdomain of it.
  The same check runs before a vendor is asked, so a vendor is never pointed elsewhere either.
- **Resolved once, and never to a private address** (the `direct` vendor): the name is
  resolved, any private, loopback, link-local or metadata address among the answers refuses
  the whole name, and the socket connects to the address that was checked (`pinnedLookup`), so
  the answer cannot change between the check and the connection.
- **A redirect never leaves the site.** Calls to a vendor follow none. Our own fetcher follows
  at most three, each only to an address that passes the same check (https, the site's own
  domain), asking the robots file again for it. The answer is capped in size, and the fetcher
  names itself in its User-Agent and obeys the site's robots file.
- **What comes back is data.** A page is never run, never followed and never shown to a
  model. Prices are read out by a recipe into fields from a fixed public list; a page is kept
  (7 days) only when nothing could be read from it.
- **Stops.** Kill switches for everything, a vendor or a site take effect at once
  (`POST /v1/admin/data-sources/switches/stop`); budgets, breakers and per-site rates are in
  `business-limits.md`.

The agent service holds at most `AGENT_DATABASE_POOL_MAX` connections (default 5) as
`suskii_agent`, which reaches only the `agent` schema, and takes `AGENT_MAX_CONCURRENT_RUNS`
(20) runs at a time per instance; more are refused and the traveller reads that the assistant is
unavailable.

Where the agent service sits when deployed (ADR-101; built, not applied): on Cloud Run it takes
internal ingress only and has no load balancer backend, so nothing reaches it from the internet;
the API calls it over the VPC with the run token. Cloud Run's invoker check is off for it: the
token and the network are the two controls, as for the worker's calls to the API. It calls
out to two places only: the API's tool gateway and the model provider. In the Helm chart a
network policy lets in the API alone. It sends nothing else anywhere: hosted tracing is refused
at start-up.

A candidate prompt in the shadow (ADR-106) sends the model provider the same scrubbed turn a
second time, with the tool results the live turn already had. No new recipient and no new kind
of data; off unless `AGENT_SHADOW_PROMPTS` names a candidate and `AGENT_SHADOW_SAMPLE_PERCENT`
is above 0.

`ssrf-guard.spec.ts`, `providers.spec.ts` and `test/price-intel.e2e-spec.ts` cover these.

## Connection limits

Each call has a deadline, and supplier calls also have circuit breakers. Each API process holds
at most `DATABASE_POOL_MAX` Postgres connections (default 10). The API's maximum instances times
that stays under Cloud SQL's `max_connections` (staging 3 x 10 against 100, production 20 x 10
against 400; ADR-059), and the `DatabaseConnectionsHigh` alert watches it. Expensive features are covered in
`business-limits.md`.
